RateWall

Feed the same requests to a token bucket, GCRA, leaky bucket, fixed window and sliding window log. See who gets through, who is denied, and which one lets a burst past the limit.

Token bucket facts

Token bucket, leaky bucket as a meter and the generic cell rate algorithm (virtual scheduling form) are described on Wikipedia as the same meter seen three ways, and here they give identical decisions on every trace (the tests check this on 600 random traces). Fixed window counts requests per aligned window, so a burst at the end of one window and the start of the next can pass up to twice the limit in a very short time. The sliding log keeps every accepted time. All policies drop denied requests (no queueing or shaping). Ties are decided in favor of the request: an arrival exactly when a token completes is accepted; Wikipedia's GCRA text writes the condition with a strict inequality, so a given implementation may differ at that exact millisecond. Times are whole milliseconds; the window must be a whole number of milliseconds. The window-length maximum counts accepted requests inside any span of the window length (window minus 1 ms, inclusive). Runs in your browser, nothing stored.
